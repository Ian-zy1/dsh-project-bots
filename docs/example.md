# 一条任务怎么走

这份公开示例使用替换后的任务标识。业务行为来自真实的站点状态页案例，示例中的新版接单事件用于解释设计。

## 1. 你说清结果，Owner 固定任务

> 已恢复的故障显示从开始到恢复的时长。尚未恢复的显示「持续中」。

Owner 把业务目的、前端改动范围、Git 基线、既有 API 和验收条件保存成固定的 `incident-duration r1`。验收包括「点击恢复后显示时长」「刷新仍一致」「非法或倒序时间可降级显示」和「原有恢复操作继续可用」。用户确认后，飞书里只发固定任务引用与一句具体范围。

## 2. Superagent 实施并交候选

DSH Router 判断接单，为原消息建立 Ticket。Worker 按同版快照在隔离工作区实现。交付时记录候选提交 SHA、验证命令和证据。独立 Reviewer 把结论关联到同一候选。

新版设计里，DSH 接单后从 Outbox 发出结构化回报，Relay 据原飞书消息匹配发起时登记的 Owner。交付回报到达后，原 Codex 会话接续复审。

## 3. Owner 看了什么，用户能看到什么

| 验收项 | 能检查的证据 |
| --- | --- |
| 已恢复事件显示耗时 | 浏览器用同一演示数据比较基线与候选，已恢复记录显示「1 小时 15 分钟」。 |
| 未恢复仍能处理 | 页面显示「持续中」，「标记恢复」可操作。点击后显示对应时长，刷新仍一致。 |
| 代码和证据对得上 | Owner 读取实际 diff，把定向测试和独立评审对应到同一候选 SHA，记下复审结论。 |

飞书原话题可查看复审结果。AW 可打开计划版本、候选与评审证据。用户比较结果后决定是否合入。
