# 复审

用于 Relay 回到原 Owner 或用户要求核对现有候选。结论针对已批准快照和实际候选 SHA。

1. **接手。** 对 Relay 事件先在原会话和项目目录按提示登记 `started EVENT_ID`，成功后继续。用户手动要求复审时按原 Ticket/Report 定位；只收到入队回执就等原会话实际接手。按需查 [原生任务与阻塞](operations.md#4-关联原生任务)。失败或阻塞只核对原因与现有证据，重试沿原任务另取授权。
2. **看实际代码。** 固定已批准的 AW 版本、摘要、仓库和基线，从原候选取得实际 diff。逐项对照计划、验收、调用路径和相关回归点。缺 Git 对象或关键材料时保留 `pending`，发现越界、遗漏或回归时给 `revise`。
3. **核实验证。** 核对测试环境、命令、结果及独立 Reviewer 原始证据，全部对应最终 SHA。已有证据充分就复用。候选变更、环境或测试覆盖不足时，只补受影响的验证与评审；页面或接口的关键使用路径缺证时补实测。证据齐全且符合计划才给 `accept`。
4. **写回。** 保存复审原件，按 [AW 候选与报告](aw.md#候选与报告) 分别保留独立评审和 Owner 复审，代录标明来源。Relay 接续按 [飞书回执](feishu.md#接手与回执) 提交证据并读回原话题；其他入口沿各自约定。说明候选、未验证项及需要用户决定的合入事项。

失败或阻塞且无候选 SHA 时，接手后直接记录实际原因、证据和下一步，结论为 `pending`。跳过候选 diff、独立评审和 AW 候选写回。Relay 事件用 `complete` 回传原件，回执省略 `candidateSha`。

## 输出模板

- 对象：AW 固定版本、原 Ticket/Assignment、基线与最终候选 SHA。
- 核对：实际改动、验收逐项结果、测试与独立评审原件、未验证项。
- 结论：`accept/revise/pending`、证据路径、已写回位置和下一步。
